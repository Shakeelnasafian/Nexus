## ADR-001: Event-Sourced Billing Subscriptions
**Date**: 2026-03-07
**Status**: Accepted

**Context**: The Billing domain is the first bounded context in Nexus that needs durable auditability and event-driven integration. The session scope required tenant-scoped `Plan` and `Subscription` models, a `SubscriptionAggregate` built on Spatie Event Sourcing, four storable billing events, a projector-maintained subscriptions read model, a reactor that dispatches dunning work on payment failure, and Pest coverage for aggregate transitions. The wider architecture also requires strict domain boundaries, multi-tenancy from day one, and no side effects inside aggregates.

**Decision**: We implemented subscription lifecycle changes as an event-sourced aggregate in [SubscriptionAggregate.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Aggregates/SubscriptionAggregate.php) and kept the aggregate limited to recording `SubscriptionStarted`, `SubscriptionRenewed`, `SubscriptionCancelled`, and `PaymentFailed` events. We modeled `Plan` and `Subscription` as tenant-scoped Eloquent models in [Plan.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Models/Plan.php) and [Subscription.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Models/Subscription.php). We projected the event stream into the `subscriptions` read table with [SubscriptionProjector.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Projectors/SubscriptionProjector.php), and we handled the only side effect in this slice through [SubscriptionPaymentFailureReactor.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Reactors/SubscriptionPaymentFailureReactor.php), which dispatches [SendDunningNotification.php](C:/xampp/htdocs/Nexus/app/Domain/Billing/Jobs/SendDunningNotification.php). We also standardized testing on Pest and covered transition behavior in [SubscriptionAggregateTest.php](C:/xampp/htdocs/Nexus/tests/Feature/Billing/SubscriptionAggregateTest.php).

**Alternatives considered**: We could have modeled subscriptions as a conventional CRUD `Subscription` model with imperative service methods and status updates in-place. We also could have embedded side effects directly in aggregate methods or used Laravel model events instead of Spatie projectors/reactors. Both options were rejected because they weaken auditability, blur domain boundaries, and make future Workflow integration depend on direct cross-domain calls instead of explicit domain events.

**Consequences**: This makes subscription history explicit, replayable, and suitable for downstream automation. It also creates a clear split between command handling in the aggregate, read model maintenance in the projector, and side effects in the reactor. The main cost is more moving parts: Billing now depends on stored-event infrastructure, projector discovery, and a read model that must stay in sync with the stream.

**Trade-offs**: The current design is stronger for lifecycle traceability and cross-domain integration, but it is heavier than a simple table-first implementation. If Billing later proves to be operationally trivial or event replay becomes unnecessary, a CRUD-style approach would be simpler. If Workflow and Accountability begin depending heavily on billing history, this decision becomes even more justified because the event stream is already the contract surface.
